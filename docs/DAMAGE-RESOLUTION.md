# Native damage multiplier and basic damage resolution (1.50.0)

Foundry 13 / PF1 11.11. The manual multiplier in PF1AE replaces only the Roll Bonuses damage multiplier; other Roll Bonuses options remain available. Native ActionUse.createAttackDialog returns the form BEFORE assigning this.formData. Empty, missing and invalid input default to 1; explicit 0 is supported. Input persists within the same dialog even on native refresh. No global last multiplier or shared Action state. Skip-dialog uses default 1. The native rollDamage hook occurs before Strength, enhancement, typed changes and extraParts (including situational bonus and Power Attack); it is no longer used for multiplication. After native generateChatAttacks, PF1AE scales complete evaluated DamageRoll totals with deterministic adjustment terms via native Roll.fromTerms, preserving die results, damage type, critical type. If reconstruction cannot be verified, abort before resources are consumed instead of re-rolling. The whole normal or critical total is rounded down once, with incremental allocation to typed components; critical total includes the normal component. Native minimum damage is normalized before scaling. This multiplier scales existing evaluated damage, not the PF1 rule of rolling extra critical dice. The underwater physical multiplier uses the same path; separate energy components are not halved.

New world setting Automatic damage defenses defaults to false. Enable for testing only with Automate Damage disabled. Direct typed native chat-card applications are resolved through pf1ApplyDamage before the original HP update. The native method remains responsible for temporary HP, nonlethal damage, actual HP and the health engine. No canvas selection lookup, no global pending card. The native Apply Damage dialog already handles many defenses; PF1AE leaves it untouched to avoid double application. Manual reductions/ratios and raw direct HP damage, healing, wounds/vigor remain native. Card full/half selection is validated against typed instances and applied once.

Supported: exact standard damage type per component (slashing, piercing, bludgeoning, acid, cold, electric, fire, sonic, force, untyped); standard immunity; highest ER per energy type per attack; standard energy vulnerability (x1.5 on non-immune damage); highest applicable basic weapon DR, bypassed by exact physical type or known magic. Nonweapon spells/touch damage ignore DR. Same energy damage components are aggregated before resistance. Only a single eligible physical type with DR is automatically processed. Multiple attacks are separate applications. Ambiguous source/mixed types, non-energy vulnerability, combined ER and vulnerability (some effects specify order), custom traits, hardness, material/alignment/complex DR, unverified magic/ammo, unsupported ability types, mismatched totals, mixed lethal/nonlethal: automatic application is cancelled (0 to native applyDamage) and the GM is warned to use the native dialog and adjust manually. Immunity to nonlethal damage is honored when the native application is nonlethal. Modifier-tag defenses (precision, area of effect) and untyped damage with DR require manual adjudication. Magic bypass currently uses the native action source exposed when applying the card; an immutable weapon/ammo attack-time snapshot is deferred. No complete Automate Damage replacement yet. No massive damage checks or ability damage migration in this stage. Native dialog currently has its own existing limitations.

Read-only API:
~~~js
const damage = game.modules.get("pf1-automation-engine").api.damageResolution;
const result = damage.preview({
  actor,
  components: [
    {value:14,types:["slashing"]},
    {value:8,types:["fire"]}
  ],
  sourceKind:"weapon", magic:true, ratio:1
});
console.log(result);
console.log(damage.lastDiagnostic(actor));
~~~
Preview returns supported/reason or incoming, total, per-type immunity, resistance, vulnerabilityBonus and damageReduction. No document mutation. The actual hook changes only options.value/ratio/reduction and supplies a diagnostic field. No automatic chat report of "applied" before native HP update completes.

Live tests: multiplier blank/re-render/skip dialog/x2/x0.5 including Strength and situational bonus; critical and mixed typed components; multiple attacks; PF1 Waters underwater and active Roll Bonuses; native full/half chat buttons; two linked/unlinked targets with different defenses; manual dialog; Automate Damage enabled/disabled. Future phases cover advanced bypasses/hardness, ability damage, custom types and migration.

## Neutral multiplier pass-through (1.50.1)

The input is blank by default with a placeholder of 1. Empty, invalid and explicit 1 values remove the PF1AE multiplier field entirely from the submitted form, rather than injecting a factor of 1. Without an independent underwater rule, no scaling state is retained and generateChatAttacks returns its native result without inspecting or reconstructing any damage rolls. Native normal and critical roll objects, arrays, terms and special corrections remain untouched. Explicit non-neutral values still scale evaluated damage; neutral manual input does not disable underwater rules.

## Already evaluated adjustment terms (1.50.2)

Foundry 13 initializes static OperatorTerms as evaluated/immutable. Do not call evaluate() again. The same guard covers NumericTerm. Only newly constructed unevaluated deterministic terms are evaluated. Never reroll existing dice. Reconstruction failure now produces an explicit notification, console stack and lastDiagnostic error instead of silent interruption. Tests simulate the actual immutable-term exception reported from Foundry 13. Live verification remains necessary.

## Multiplicative display (1.50.3)

The verified additive adjustment is still the authoritative native DamageRoll representation; presentation only changes. Validated metadata in Roll.options records the pre-multiplier formula, total, factor, native minimum correction and allocated total. The PF1 DamageRoll toAnchor tooltip and expanded getTooltip show `(native formula) × factor = product` and, where needed, a separate global rounding allocation. The exact final adjustment row is visually replaced, never removed from the underlying roll. Original dice, numerical modifiers, typed totals, serialized inline roll and apply-damage buttons are untouched. Unknown layout or unmatched adjustment falls back to native detail. Neutral rolls carry no display metadata. Tested with the PF1 11.11 tooltip structure in a simulated DOM; actual Foundry rendering still needs validation.

## Foundry 13 inline anchor tooltip (1.50.4)

PF1 11.11 source `module/utils/chat.mjs` explicitly uses `dataset.tooltipText` in Foundry 13, rather than `dataset.tooltip`. The DamageRoll anchor wrapper now replaces the native formula in `data-tooltip-text` as plain text, with a legacy escaped HTML fallback. The `pf1PreDisplayActionUse` hook additionally checks the exact normal/critical `ChatAttack.damageRows` and their finalized `inlineRoll` anchors, before rendering `attack-roll.hbs` (see `module/action-use/chat-attack.mjs`, `module/action-use/action-use.mjs`). No serialized data or arithmetic is changed. Missing, obfuscated, custom or HTML tooltips remain untouched; PF1's native obscuring behavior is preserved. New cards only. Tests exercise both actual v13 attributes and the native pre-display lifecycle; live verification required.

## Per-target native DamagePartModel clone (1.50.5)

PF1 11.11 `module/utils/chat.mjs` assigns `d.value = dmg.total` outside the DamagePartModel schema. `module/documents/actor/actor-pf.mjs` static applyDamage clones each part using `new DamagePartModel(i.toObject())`; the native schema (`module/models/action/damage-part-model.mjs`) only includes formula and types. This loses the evaluated amount on direct application. PF1AE recovers evaluated amounts from the exact message.systemRolls.attacks[attackIndex].damage and, for critical buttons, critDamage. It verifies the native button, exact attack identity, component count and type sets, any surviving instance values, button ratio and total. No reroll and no mutating the message or cloned instances. Mismatches fail closed. Native manual dialog remains excluded. Regression tests reproduce the actual schema clone, not just plain objects with value. Live Foundry validation required.

## Melee material DR (1.51.0, first stage)

The preceding 1.50.x restrictions are extended only for single-material DR against a manufactured melee weapon with no ammunition. The real user diagnostic (PF1 11.11 / Foundry 13.351) has action.normalMaterial="steel", action.addonMaterial=[], action.enhancementBonus=null, item.system.enh=null, explicit non-custom materials, action.ammo.type=null, and target DR {amount:5,types:["silver"],operator:true}. With 12 slashing damage the expected result is 7. The effective action normal and addon materials, not the item's raw base material or localized labels, determine bypass. Recognized silver, alchemicalSilver and mithral overcome silver DR; coldIron and adamantine overcome the corresponding DR. Enhancement +3 substitutes for silver/cold iron; +4 for adamantine DR, never hardness. The highest remaining DR applies once per attack including critical; the native damage application is otherwise unchanged.

Read-only preview additionally accepts material:{normal:"steel",addons:[],enhancement:0} with sourceKind:"weapon". In the live adapter this profile is only constructed from the verified melee action context. Unknown material/bonus provenance fails closed unless a verified positive bypass is established. Custom material flags, ammunition, natural attacks, alignment DR, multi-criterion DR and hardness remain manual. Paizo's Core Rulebook FAQ explicitly excludes launcher-derived enhancement for material DR; ranged attacks therefore remain deferred. Current action data can change between roll and application: immutable weapon/ammo attack-time snapshot remains deferred; use manual adjudication if the source was changed after the roll. No new settings. Tests simulate the supplied native structure and verify half/critical/multiple attack, positive and negative material cases and unsupported cases. Live validation is still required, especially the identifiers other than steel/silver and effective addon representation.

## Native silver DR identifier (1.51.1)

The second live diagnostic reports target DR {amount:5,types:["alchemicalSilver"],operator:true}, not ["silver"]. The exact single criterion is normalized locally to silver before bypass evaluation; native actor traits are never changed. Both native application and read-only preview are covered by the 19 slashing / mundane steel → 14 regression. Silver aliases, mithral, +3 enhancement, half/critical damage, highest remaining DR and unknown/combined criteria are tested. User-reported 1.50.5 live acceptance: all eleven base damage scenarios passed. The new material cases still require live validation.

## Combined and alignment DR (1.51.2)

Single-type rows ignore operator. Multi-criterion rows use native-style operator true=OR and false=AND (corroborated by Automate Damage scripts/main.js, not independently verified against exact PF1 11.11 source). Missing/nonboolean operator is indeterminate. Criteria are evaluated individually with true/false/unknown; decisive true OR or false AND short circuits uncertainty. Only the highest remaining DR applies; unknown rows only block if their amount could change the final damage. One physical damage type per attack remains required.

Manufactured melee with no ammo: explicit action alignment true/false overrides item.system.alignments, null inherits. Actual +5 enhancement bypasses alignment DR, not the character's personal alignment. A matching alignment subtype also bypasses; only an explicit prepared actor.system.traits.creatureSubtypes.total collection is accepted for subtype evaluation. This path is a provisional adapter pending exact PF1 11.11 live verification; absent or custom subtype data is unknown, not an empty set. A positive weapon flag or +5 is sufficient without subtype information. Negative alignment requires verified absence of matching subtype and known enhancement. No claim of support for natural attacks or projectile alignment yet. Preview may supply alignment:{values:{good:true},enhancement:0}. No persistent data writes. Tests simulate the operator convention, overrides, unknown and matching subtype, +5, combinations, highest DR, critical and half. User confirmed 1.51.1 silver RD works; further in-world tests deferred at user's request.

## Persistent damage source snapshot (1.51.3)

At pf1PreDisplayActionUse (after native rolls are finalized, before native ChatMessage creation), attach flags["pf1-automation-engine"].damageSourceSnapshot to ActionUse.shared.chatData, following the existing save-context.js mechanism. Version 1 stores exact source actor/item UUID, item/action ID, attack count and detached, JSON-safe sourceKind, magic, material and alignment profiles. It is captured even with the damage defense option off (generic engine enabled), once per chat data object. No global pending attack, no post-create write, no new message, no serialized roll mutation. All attacks in that action card currently share the same source profile. Capture is at finalization rather than the instant of each individual die roll; a future per-attack ammo adapter must handle heterogeneous projectiles separately. Current native hook contract and identity fields are modeled, not newly verified in a live world.

At apply, validate schema, exact action/item/actor provenance and attack count/index against the native card and/or matching live identity; current weapon properties are never consulted for a captured card. Target defenses are evaluated at application time as before. If no snapshot exists, legacy source kind is classified from the native action only, never its current magic/material/alignment. Missing/invalid/mismatched profiles produce manual adjudication when they can affect damage. Valid energy or simple physical results remain available where independently decidable. The flag is not an authorization boundary or cryptographic signature. API damageResolution.sourceSnapshot(message) returns a detached normalized record or null; lastDiagnostic includes sourceSnapshot state captured/missing/invalid/mismatch. Native dialog excluded as before. Tests simulate serialization, source mutation, multiple cards/attacks, deleted source with exact native IDs, missing/invalid identity and opt-in changes. Live two-client, reload, synthetic actor and hook timing tests deferred. Natural attack and ammo provenance remain separate future work.

## Natural weapons and innate bypass (1.51.4)

PF1 Bestiary universal monster rule Damage Reduction (https://pathfinder.dragonlash.com/rules/universal-monster-rules/damage-reduction/) and Paizo FAQ on Amulet of Mighty Fists (https://paizo.com/paizo/faq/v5748nruor1fm). Native attack type and subtype are documented in the public PF1 API sheetSections/ItemAttackPF; public ItemAction getter docs describe enhancementBonus and normalMaterial as nullable. The exact installed PF1 11.11 implementation has not been independently inspected. Natural melee item classification requires Item type attack, subtype natural, no conflicting subtype or ammo/ranged context. A positive prepared own DR/magic or DR/epic qualifies natural attacks, not manufactured weapons, and never fabricates a numeric enhancement or material. Alignment subtype is separate from the creature's DR or personal alignment. Native configured enhancement thresholds work as with manufactured weapons; external buffs not represented by the native getter, spell-specific restrictions, special ability bonus equivalents for epic and custom provenance are not solved. Actual +6 or innate DR/epic gives an explicit epic bypass; unknown equivalent bonus remains manual. Ordinary natural profile uses a nonmaterial sentinel when the effective getter is explicitly null with known addons; custom/unknown material stays unresolved. No unarmed or ranged natural classification by names. The snapshot adds optional epic tri-state to schema 1; old cards are readable with epic unknown and are never retroactively enriched. Recreate natural attack cards after update. Regression suite covers exact source, innate effects, negative inheritance, combos, enhancement, snapshots and invalid/old flags. Live integration tests remain deferred.

## Projectile and thrown weapon DR (1.51.5)

Paizo Core Rulebook FAQ (https://paizo.com/paizo/faq/v5748nruor1fm): a projectile weapon +1 grants magic bypass and explicit alignment is transmitted; launcher enhancement does not confer higher material/alignment/epic bypass thresholds. The projectile's own actual enhancement is evaluated independently. Native explicit thrown action twak with no ammo uses the weapon itself. PF1FR reload-core.js uses shared.attacks[].ammo.id and its native getAmmo adapter exposes {id,document,data}; PF1AE wraps only the instance generateChatAttacks, records detached profiles before calling the existing native/wrapped method unchanged, and adds a perAttack array to the existing card snapshot. No ammo consumption, reload state or rolls changed. Owned ammo document and compatible subtype are verified; legacy loot/ammo requires explicit native default link. Homogeneous profiles require exact attack count, mixed require explicit chat entry ammo IDs and matching multiset; otherwise all projectile-specific properties are unknown. No selection by name/default fallback or guessing mixed order. Native mapping and data fields need live confirmation; PF1FR currently refuses mixed loaded ammunition. No change to PF1FR repo.

Ammo native material getters/alignments/enh when present, or PF1 item dictionary flags Material (exact recognized ID, e.g. alchemicalSilver), Alignment (one ID good/evil/lawful/chaotic), and boolean Magic, as documented by Automate Damage. PF1AE additionally defines dictionary Enhancement (nonnegative integer, actual projectile enhancement; no change to attack/damage roll). Missing numeric enhancement with known flag containers is treated as 0 unless Roll Bonuses is active under the observed module ID; other external bonus providers and conditional modifiers are not inferred. Explicit conflicts/unknown values stay unresolved. No arbitrary damage bonus counts as enhancement. The epic equivalent bonus is still unresolved except verified actual +6. These are adapters, not confirmation of exact native 11.11 schema. Recreate cards after update. Regression simulations cover launcher/material separation, magic/alignments, mixed order, unknown mapping, source identity, deletion/mutation timing, legacy PF1FR ammo, thrown weapons. Live tests deferred.

## Hardness and ordinary object damage (1.51.6)

PF1 Core Rulebook, Breaking and Entering (https://pathfinder.dragonlash.com/rules/additional-rules/exploration/breaking-and-entering/); universal monster rule Hardness (https://pathfinder.d20srd.org/bestiary/universalMonsterRules.html); Paizo Core Rulebook FAQ (https://paizo.com/paizo/faq/v5748nruor1fm) clarifies adamantine bypasses hardness strictly below 20, not 20. Native character/npc traits.hardness is applied once per hit after normal defenses; creatures do not suffer object energy/ranged halving. Actual verified adamantine on the weapon/projectile (not enhancement substitution) bypasses hardness on physical weapon damage only; other components still face hardness. The ordering of simultaneous flat reductions is an implementation choice (existing DR/ER first); combinations with vulnerability and consequential unknown material fail closed. No inferred material from weapon name. Native application behavior with positive hardness needs live verification against PF1 11.11; no direct HP change is made by PF1AE.

For an actor explicitly representing an **ordinary inanimate object**, GM may set the world Actor flag `await actor.setFlag("pf1-automation-engine","objectDamageMode","standard")` (unset to restore). This is an explicit standard-object rules selection, not an automatic construct or vehicle classifier. Standard object energy or ranged physical weapon damage is halved per eligible component before hardness; no double object adjustment of one component, normal save half still applies. Object damage ignores additional native critical rolls after validating full card total, and nonlethal is immune. Precision-tagged damage requires review; no arbitrary immunity to custom types. Siege/vehicle rules, unusual damage/material interactions and object-specific exceptions are not automated; use manual adjudication. Vehicles with positive hardness require explicit classification rather than assuming ordinary objects. The snapshot adds optional delivery melee/ranged/other; older cards remain readable but lack verified object delivery. No automatic broken/destroyed flag or inventory item update.

Read-only `api.damageResolution.previewObject({hardness:5,hp:20,maxHp:20,components:[{value:16,types:["slashing"]}],sourceKind:"weapon",delivery:"melee",material:{normal:"steel",addons:[],enhancement:0}})` returns total 11 and projected remaining 9, broken true (half HP or less), destroyed false. This is a calculation helper for manually resolved object damage/sunder, not a CMB test, equipment selection or transaction. If special effects modify broken threshold, destruction, object damage or hardness, use the appropriate manual rule. Tests simulate all above cases; actual target flags, native applyDamage, mixed damage ordering and multiplayer are unverified in a live world. Recreate cards for delivery capture.

## Ability score operations (1.52.0, first stage)

PF1 Core Rulebook special abilities (https://legacy.aonprd.com/coreRulebook/glossary.html) distinguishes damage (penalties per two points), drain (actual score reduction), and penalties (cannot alone cause unconsciousness/death). Bestiary undead traits: immune to all ability drain and physical ability damage/penalties; constructs are not subject to ability damage/drain. Source-specific exceptions, immunities and saves remain caller responsibility. Public PF1 AbilityData docs and Automate Damage use stored damage, drain, userPenalty fields. Exact installed PF1 11.11 source and prepared recalculation are not independently verified. Do not add manual derived modifiers, HP, unconscious/dead conditions or rest healing in addition to native recalculation. The actual zero-score behavior, penalty floor, CON/CHA HP recalculation and immunity ID/type schema need live verification.

```js
const api = game.modules.get("pf1-automation-engine").api.abilityDamage;
const operations = [{ability:"str",kind:"damage",operation:"inflict",amount:3}];
console.log(api.preview({actor,operations}));
console.log(await api.apply({actor,operations,requestId:foundry.utils.randomID()}));
```

Operations: six canonical ability IDs; damage/drain accept inflict/restore with nonnegative integral amount; restore floors at zero. Penalty accepts only set (absolute resolved native manual penalty total, including zero); caller owns stacking, duration and expiration. No duplicate field per request. Source values via Actor.toObject(), prepared traits.type and explicit standard abilityDamage/abilityDrain/abilityPenalty when present. Unknown native/custom immunity requires explicit GM confirmation; built-in known immunity remains respected. Missing or nonpositive base score cannot receive a new loss unless immunity already establishes zero. No automatic poison/curse/fortitude save handling. No arbitrary custom damage type interpretation. No automatic chat ability-damage application yet, and existing HP damage engine continues to reject unknown types when automatic defenses are enabled.

Apply requires owner or GM and automatic defense engine active without Automate Damage; preview is read-only. Stable requestId required (caller reuses the same ID for the same operation, not a new random ID on retry); last 32 receipts stored on the same actor update with native fields. Local lock only, not cross-client compare-and-swap. Conflicting reuse is refused. Network failure or post-update discrepancy is unconfirmed: inspect actor and receipt before retry. No mutation of base score, derived data or HP. Tests simulate native field updates, immunities, restoration, authorization, duplicate, error and local concurrency. Future work: native card custom type registry/verified mapping, separate awaitable application path, per-source duration/penalty tracking, threshold behavior and live verification. This stage does not claim replacement of Automate Damage.

## Ammunition properties (1.52.1)

The native loot/ammo or ammo sheet exposes a PF1AE fieldset in Details when available. Owner/GM explicit save persists schema 1 under flags.pf1-automation-engine.ammunitionProperties; no native schema replacement. API ammunition.inspect(item), save(item,profile), previewBonus({launcherEnh,launcherMasterwork,ammoEnh,ammoMasterwork}), lastDiagnostic(). Legacy numeric ammo-enhancement from Roll Bonuses and PF1 dictionary Material/Alignment/Enhancement + Magic can be read; incompatible formulas, stacking, bane, additional attack/damage/effect flags require manual migration, never deleted. Saving is disabled while Roll Bonuses is active. The world option ammunitionBonuses defaults on but runtime adjustment is suspended with ckl-roll-bonuses active. Other Roll Bonuses functionality is not replaced.

Native hook pf1CreateActionUse installs per-instance _getConditionalParts wrapper (contract corroborated by Roll Bonuses src/main.mjs and src/bonuses/ammunition.mjs, exact installed PF1 11.11 source not independently verified). For selected exact owned ammo, append only max(launcher,ammo,masterwork)-native launcher attack bonus and max(launcher,ammo)-launcher damage. Normal typed damage conditional is intended to multiply on critical and be included before existing damage multiplier. Primary damage must have one recognized physical type; unknown native structure is reported, not patched. No native rolls repeated, inventory or launcher mutation, or PF1FR changes. Existing projectile capture uses the same profile for RD and retains projectile-only enhancement bypass. Active Roll Bonuses plus PF1AE-stored enhancement is treated as unknown for RD rather than automatically applying a new roll bonus. Exact native fields, critical typing/stacking, render selectors, mixed ammo and Roll Bonuses coexistence require live tests. Test suite uses simulated conditional result. No replacement of arbitrary ammo attack/damage formulas, bane, notes, special bonuses, or conditional stacking yet.
